# ทำนายโอกาสการเกิดอุบัติเหตุบนถนน (ประเทศไทย)

รวมข้อมูล 4 ด้าน — **ประวัติอุบัติเหตุ / ลักษณะเส้นทาง / สภาพอากาศ / เทศกาล** —
เป็นชุดข้อมูลระดับ **จังหวัด × วัน** สำหรับเทรนโมเดลทำนายโอกาสการเกิดอุบัติเหตุ
เป้าหมายปลายทางคือใช้ผลไปวางแผนป้องกันและลดอุบัติเหตุ

```
Node.js  ->  ดึง + รวมข้อมูล  ->  data/processed/panel.csv  ->  Python  ->  โมเดล
```

---

## ⚠️ ข้อจำกัดที่ต้องรู้ก่อนใช้ผลไปตัดสินใจ

**1. ครอบคลุมเฉพาะโครงข่ายถนนของกระทรวงคมนาคม**
target หลักมาจากข้อมูลอุบัติเหตุบน **ทางหลวง + ทางหลวงชนบท + ทางพิเศษ** เท่านั้น
**ไม่รวมถนนในเมือง ถนนท้องถิ่น และซอย**

เทียบให้เห็นภาพ — ปี 2565 ชุดนี้บันทึกผู้เสียชีวิต 2,619 คน ขณะที่ข้อมูลบูรณาการ 3 ฐาน
(ครอบคลุมทุกถนน) มี 17,379 คน → **โครงข่ายนี้จับได้ราว 15% ของการตายบนถนนทั้งประเทศ**
โมเดลจึงบอก "ความเสี่ยงบนทางหลวง" ไม่ใช่ "ความเสี่ยงบนถนนทุกสายในจังหวัด"

**2. `สภาพอากาศ` และ `ลักษณะทาง` ในข้อมูลดิบ ใช้เป็น feature พยากรณ์ไม่ได้**
สองคอลัมน์นี้มีค่าก็ต่อเมื่อ*เกิดอุบัติเหตุไปแล้ว* ถ้าเอาเข้าโมเดลตรง ๆ จะได้ค่าความแม่นสูงแบบหลอก ๆ
แล้วใช้งานจริงไม่ได้ (data leakage) โปรเจกต์นี้จึงใช้:
- **สภาพอากาศสำหรับพยากรณ์** → Open-Meteo (มีทุกวัน ทุกจังหวัด ไม่ว่าจะเกิดเหตุหรือไม่)
- **ลักษณะทาง** → สรุปเป็นโปรไฟล์รายจังหวัดจาก**ปีก่อนหน้าเท่านั้น** (`pct_curve_prev` ฯลฯ)
- คอลัมน์ `check_rain_reported` เก็บไว้**ตรวจสอบข้อมูล ห้ามใช้เทรน** และถูกกันออกจาก feature set แล้ว

**3. ข้อมูลจบที่ 2026-04-30 และมี reporting lag** เดือนท้าย ๆ ตัวเลขจะต่ำกว่าความจริง
มีคอลัมน์ `is_recent_90d` ไว้กรองช่วงที่ข้อมูลยังไม่นิ่งออกได้

**4. ThaiRSC ให้เฉพาะยอดสะสมของปีปัจจุบัน** ใช้ทำอนุกรมเวลาย้อนหลังไม่ได้
โปรเจกต์นี้จึงใช้ ThaiRSC เป็น**ข้อมูลอ้างอิงรายจังหวัด** (ประชากร รถจดทะเบียน พื้นที่) เท่านั้น
ถ้าต้องการตัวเลขรายวันแบบเรียลไทม์ ต้องตั้ง cron เก็บ snapshot เอง (เป็นงานแยก)

**5. ขยายช่วงปีได้** ต้นทางมีข้อมูลถึงปี 2562 (2019) เพิ่ม resource id ใน `src/config.js` ได้เลย

## วิธีใช้

```bash
node src/cli.js build            # ดึงข้อมูล + สร้าง panel.csv + hotspots.csv
node src/cli.js build --with-osm # ดึง OpenStreetMap เพิ่ม (ช้ามาก ดูหมายเหตุด้านล่าง)
node src/cli.js provinces        # สร้างไฟล์อ้างอิงจังหวัดใหม่
node src/cli.js ingest           # อุ่น cache อย่างเดียว ไม่เขียนไฟล์ผลลัพธ์
```

รอบแรกใช้เวลา ~6 นาที (ดาวน์โหลด CSV ~100MB + Open-Meteo)
ทุกอย่างถูก cache ลง `data/raw/` รอบถัดไปจึงเร็วมาก

**Open-Meteo จำกัดอัตราการเรียกค่อนข้างเข้ม** โค้ดหน่วง 15 วินาทีระหว่างชุด
และถอยยาว 30/60/120 วินาทีเมื่อเจอ HTTP 429 ถ้ายังล้ม ให้รันซ้ำ — ชุดที่สำเร็จถูก cache ไว้แล้ว

**OpenStreetMap ถูกปิดเป็นค่าตั้งต้น** — Overpass สาธารณะ rate-limit หนักกว่า Open-Meteo มาก
(ทดสอบจริงแล้วติดตั้งแต่จังหวัดที่ 3 จาก 77 ต้องรอเป็นชั่วโมง) ซึ่งไม่คุ้ม เพราะ
**ลักษณะโครงข่ายถนนมีจากกรมทางหลวงอยู่แล้ว** (`highway_km`, `avg_lanes`, `vehicle_km` รายจังหวัด)
บวกกับโปรไฟล์ลักษณะทางจากข้อมูลอุบัติเหตุเอง (`pct_curve_prev` ฯลฯ)
ถ้าอยากได้ `osm_*` เพิ่มจริง ๆ ใส่ `--with-osm` แล้วปล่อยรันยาว ๆ (cache ไว้ให้ครั้งเดียวจบ)

## ผลการเทรน (รันจริงแล้ว)

เทรนทั้ง **LightGBM และ XGBoost** บนเงื่อนไขเดียวกันทุกอย่าง — feature ชุดเดียวกัน,
การแบ่งข้อมูลเดียวกัน, calibration และวิธีเลือก threshold แบบเดียวกัน
(`num_leaves=63` ของ LightGBM กับ `max_depth=6` ของ XGBoost ให้จำนวนใบสูงสุดเท่ากันคือ 64)

แบ่งตามเวลา: train 2022–2023 / valid 2024 / **test 2025** / holdout 2026 (ม.ค.–เม.ย.)

### เทียบสอง algorithm บนชุด test

| | LightGBM | XGBoost |
|---|---|---|
| ROC-AUC | 0.7440 | **0.7445** |
| PR-AUC | 0.7118 | **0.7141** |
| Brier (ต่ำ=ดี) | 0.1997 | **0.1994** |
| accuracy @0.50 | 0.6945 | **0.6948** |
| F1 @0.50 | 0.5931 | **0.5940** |
| F1 @0.32 (threshold ที่จูนจาก valid) | 0.6566 | **0.6589** |
| F1 holdout 2026 | 0.6823 | **0.6847** |
| MAE จำนวนครั้ง (ต่ำ=ดี) | **0.7487** | 0.7649 |
| จำนวนต้นไม้ที่ใช้จริง | 87 | 153 |

**ส่วนต่างเล็กมากจนถือว่าเสมอกัน** — PR-AUC ต่างกัน 0.0023 ซึ่งอยู่ในระดับ noise
XGBoost ชนะฝั่ง classification ทุกช่อง แต่แพ้ฝั่งทำนายจำนวนครั้ง
ข้อสรุปที่ได้จึงไม่ใช่ "XGBoost ดีกว่า" แต่คือ **เพดานอยู่ที่ข้อมูล ไม่ใช่ที่ algorithm**
สอดคล้องกับที่ทั้งคู่ early-stop เร็ว (87 และ 153 ต้น จากเพดาน 2,000)

### รายละเอียดชุด test (XGBoost, n=28,105, วันที่เกิดเหตุจริง 43.7%)

| | acc | precision | recall | F1 | ROC-AUC | PR-AUC | Brier |
|---|---|---|---|---|---|---|---|
| โมเดล @0.50 | 0.695 | 0.709 | 0.511 | 0.594 | **0.745** | **0.714** | 0.199 |
| โมเดล @0.32 | 0.653 | 0.577 | 0.767 | **0.659** | 0.745 | 0.714 | 0.199 |
| baseline จังหวัด × วันในสัปดาห์ | 0.659 | 0.650 | 0.473 | 0.548 | 0.705 | 0.674 | 0.213 |

ชุด holdout ปี 2026 ได้ **F1 0.685 / PR-AUC 0.742** ซึ่ง*ดีกว่า* test เล็กน้อย
แปลว่าโมเดลไม่ได้เสื่อมตามเวลา — เป็นสัญญาณว่าไม่ได้ overfit ช่วงเวลาใดเวลาหนึ่ง

**อ่านตัวเลขนี้อย่างไรให้ไม่หลงตัวเอง**
- accuracy 69% ฟังดูดี แต่ถ้าเดา "ไม่เกิด" ทุกวันจะได้ 56.3% อยู่แล้ว ส่วนต่างจริงคือ ~13 จุด
- **ตัวที่ควรดูคือ PR-AUC** — โมเดล 0.711 vs baseline 0.674 ชนะจริงแต่ไม่ขาด
- threshold เลือกจากชุด valid เท่านั้น แล้วล็อกไปใช้กับ test/holdout ไม่ได้จูนบนชุดทดสอบ
- ที่ threshold 0.32: จับวันที่จะเกิดเหตุได้ **77%** แลกกับความแม่นยำ 57% (เตือนผิด 7,024 วัน-จังหวัด)
  เหมาะกับงานตั้งด่าน/รณรงค์ที่ยอมเตือนเกินได้ ถ้าต้องการแม่นกว่านี้ให้ขยับ threshold ขึ้น

### ข้อมูลแต่ละด้านมีน้ำหนักเท่าไร — วัดด้วย SHAP

`feature_importances_` ของสอง library เทียบกันไม่ได้ (LightGBM นับ *split count*,
XGBoost ใช้ *gain*) จึงใช้ **mean |SHAP| บนชุด test ทั้ง 28,105 แถว** แทน —
อยู่ในหน่วย log-odds เหมือนกันทั้งคู่ เทียบข้าม algorithm ได้ตรง ๆ

| กลุ่มข้อมูล | LightGBM | XGBoost |
|---|---|---|
| ประวัติอุบัติเหตุ | 49.6% | 43.9% |
| **ลักษณะเส้นทาง** | 16.5% | 15.0% |
| เวลา/ฤดูกาล | 12.6% | 17.3% |
| **เทศกาล/วันหยุด** | 10.2% | 10.6% |
| การเปิดรับความเสี่ยง | 5.6% | 6.7% |
| **สภาพอากาศ** | 5.5% | 6.4% |

**ตอบโจทย์ตั้งต้นได้แล้ว**: ประวัติอุบัติเหตุคุมเกือบครึ่ง ตามด้วยลักษณะเส้นทาง ~15%
เทศกาล ~10% และสภาพอากาศ ~6%

ทั้งสอง algorithm ให้ตัวเลขใกล้กันเกือบทุกกลุ่ม (ต่างกัน ≤ 4.8 จุด) ยกเว้น
ประวัติอุบัติเหตุ vs เวลา/ฤดูกาล ที่สลับน้ำหนักกัน 5.6 จุด — สองกลุ่มนี้ทับซ้อนกันเอง
เพราะต่างก็เข้ารหัสรูปแบบตามเวลา จึงไม่ใช่ความขัดแย้งที่น่ากังวล
**ข้อสรุปเรื่องอากาศกับเทศกาลตรงกันแทบเป๊ะ** จึงเชื่อถือได้

feature เดี่ยวที่แรงที่สุด (XGBoost, mean |SHAP|):
`acc_roll28_prev` 23.9% · `acc_same_dow_mean_prev` 15.2% · `days_since_start` 13.0% ·
`vehicle_km` 9.4% · **`is_seven_dangerous_days` 6.1%** · `acc_roll7_prev` 4.8%

### สองเรื่องที่ SHAP บอกแล้วเอาไปใช้ได้เลย

**ฝนตกเท่าไรถึงเริ่มอันตราย** (`shap_dependence_rain.png`)
SHAP ข้ามศูนย์ที่ราว **4–5 มม./วัน** แล้วไต่ขึ้นชันจนถึง ~20 มม. หลังจากนั้นอิ่มตัว
→ ฝนปรอย ๆ แทบไม่เพิ่มความเสี่ยง แต่พอเกิน 5 มม. ต้องเริ่มระวัง
และฝน 50 มม. ก็ไม่ได้อันตรายกว่า 20 มม. มากนัก

**วันหยุดยาวแค่ไหนถึงน่ากลัว** (`shap_dependence_festival.png`)
ไม่ได้เพิ่มแบบไล่ระดับ แต่เป็น**จุดหักศอกที่ 4 วัน** —
หยุด 0–3 วัน SHAP ≈ 0 (แทบไม่ต่างจากวันปกติ) แต่พอหยุด 4 วันพุ่งเป็น +0.18
และ 5 วันเป็น +0.32 log-odds
→ ทรัพยากรป้องกันควรทุ่มไปที่ช่วงหยุดยาว 4 วันขึ้นไปเป็นหลัก

โมเดลจำนวนครั้ง (Poisson): MAE **0.749** (LightGBM) / **0.765** (XGBoost) เทียบ baseline 0.944

⚠️ ตัวเลขเหล่านี้บอก **"อิทธิพลต่อการทำนายของโมเดล"** ไม่ใช่ **"สาเหตุของอุบัติเหตุ"**
เป็นความสัมพันธ์ ไม่ใช่ causation

ดูรายละเอียดเต็มที่ `train/artifacts/{lightgbm,xgboost}/metrics.json` (คีย์ `shap`)
และภาพ `shap_groups.png`, `shap_summary.png`, `shap_dependence_*.png`, `calibration.png`
ส่วน `train/artifacts/comparison.json` เก็บผลของทั้งสองไว้ในไฟล์เดียว

## เรื่องที่ข้อมูลต้นทางไม่นิ่ง และโค้ดรับมืออย่างไร

ชุดข้อมูลราชการไทยเปลี่ยนรูปแบบเกือบทุกปี โค้ดจึง**เดาจากข้อมูลจริง ไม่ hard-code ตามปี**

**รูปแบบวันที่เปลี่ยนทุกปีในไฟล์ชุดเดียวกัน**

| ปี | รูปแบบ | ตัวอย่าง |
|---|---|---|
| 2565, 2566 | `M/D/YYYY` | `01/01/2022` |
| 2567, 2568 | เลข serial ของ Excel | `45292` |
| 2569 | `D/M/YYYY` | `1/1/2026` |

`detectDateFormat()` ใน `src/lib/dates.js` ดูค่าจริงทั้งไฟล์แล้วสรุปเอง
แล้ว **assert ว่าปีที่ parse ได้ตรงกับคอลัมน์ `ปีที่เกิดเหตุ` ทุกแถว** — ถ้าไม่ตรงจะหยุดทันที
(นี่คือจุดที่พังเงียบได้ง่ายที่สุด สลับวัน/เดือนแล้วไม่มีใครรู้)

**ชื่อคอลัมน์เปลี่ยน** `KM` ↔ `ก.ม.`, `บริเวณที่เกิดเหตุ` ↔ `บริเวณที่เกิดเหตุ/ลักษณะทาง`
→ `MOT_COLUMNS` ใน `src/config.js` เก็บชื่อที่เป็นไปได้ทั้งหมด แล้วเลือกอันที่เจอ

**encoding ไม่เหมือนกัน** ไฟล์ RTDDI ปี 2565/2566 เป็น TIS-620 ปีหลังเป็น UTF-8
→ `decodeBuffer()` ลอง UTF-8 แบบ fatal ก่อน พังแล้วค่อยตกไป `windows-874`

**คอลัมน์พิกัดสลับกันไม่เหมือนกันในแต่ละปี** ปี 2565 ถูก ปี 2567/2569 สลับ
→ `orientCoords()` แยกด้วยช่วงค่าแทนชื่อคอลัมน์ (ละติจูดไทย 5–21, ลองจิจูด 96–106 ไม่ทับกัน)

**ชื่อจังหวัดหายหรือสะกดไม่ตรง** ปี 2567 มีจังหวัดว่าง 1,929 แถว (8% ของปีนั้น)
ถ้าทิ้งไปเฉย ๆ ปีนั้นจะต่ำผิดปกติจนโมเดลเรียนรู้ผิด → `recoverMissingProvinces()` กู้คืนด้วย
รหัสสายทางก่อน (ทางหลวงชนบทใช้อักษรย่อจังหวัดนำหน้า เช่น `นธ.4011`)
แล้วค่อยใช้ kNN บนพิกัดจากจุดที่ระบุจังหวัดสำเร็จแล้วนับหมื่นจุด
→ **สุดท้ายกู้คืนได้ 1,949 แถว เหลือกู้ไม่ได้เพียง 2 แถว**

## การตรวจสอบความถูกต้อง

`npm run build` จะ assert อัตโนมัติก่อนเขียนไฟล์ — ล้มดังดีกว่าปล่อยข้อมูลผิดออกไป:
จำนวนแถวต้องครบ, ไม่มี (จังหวัด, วันที่) ซ้ำ, ยอดรวมต้องตรงกับจำนวนเหตุการณ์ที่โหลดมา,
ข้อมูลอากาศหายน้อยกว่า 1%, และไม่มีคอลัมน์ที่ทำให้ leak หลุดเข้า feature set

นอกจากนี้มี spot-check ที่รันแล้วผ่านจริง:

| ตรวจอะไร | ผล |
|---|---|
| ปี 2569 ต้องมีข้อมูลแค่ ม.ค.–เม.ย. | ✅ ม.ค. 2,631 / ก.พ. 1,893 / มี.ค. 1,743 / เม.ย. 2,471 |
| ช่วงสงกรานต์ต้องเสี่ยงกว่าวันปกติ | ✅ 2.51 vs 0.79 ครั้ง/จังหวัด/วัน = **3.18 เท่า** |
| **ฝนจาก Open-Meteo ต้องตรงกับที่บันทึกจริง ณ จุดเกิดเหตุ** | ✅ **20.0% vs 2.9% = 6.84 เท่า** |

ข้อสุดท้ายสำคัญที่สุด เพราะเป็นการยืนยันว่า join พิกัด × วันที่ ถูกต้องจริง
โดยเทียบกับแหล่งข้อมูลที่เป็นอิสระจากกันคนละแหล่ง
